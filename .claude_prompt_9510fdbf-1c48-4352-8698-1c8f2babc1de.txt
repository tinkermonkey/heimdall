**Title**:
Phase 2: Hover-driven navigation edge visibility

**Description**:
Implements the collapse-aware rules that determine which navigation-route edges become visible when a user hovers a page or view node. Navigation routes are hidden by default and only appear on hover, with different route sets depending on whether the hovered page's view subtree is expanded or collapsed.

## Requirements
- Navigation route edges are not shown by default; they appear on hover of a page or view node (FR 20, US-8/US-9)\n- Hovering a page whose view subtree is NOT expanded shows routes belonging to that page AND its child views, but NOT its descendant sub-pages (FR 21, US-8)\n- Hovering a page whose view subtree IS expanded shows only routes directly attributed to that page itself (FR 22, US-9)\n- Hovering a view node shows only the navigation routes directly attributed to that view (FR 23, US-9)

## Design Guidance
Implements the \"Navigation Edge Visibility (uxNavEdgeVisibility.ts)\" section of the architecture: the visibility rules table (page/collapsed, page/expanded, view, no-hover) and the `visibleNavigationEdgeIds()` function that derives the hover \"source set\" using `forest.childrenOf` and `isPageNode`. Integrates with the existing edge-visibility check in GraphCanvas (extending, not replacing, the current `hidden` computation) as described in \"Integration\" and reuses `structuralDescendants` per \"Component Reuse\" — no new traversal primitives.

## Acceptance Criteria
- [ ] With no hover and `showAllRelations` unset, no navigation routes are visible\n- [ ] Hovering a collapsed page shows navigation routes from the page itself and its child views, and does not show routes from descendant sub-pages\n- [ ] Hovering an expanded page shows only navigation routes directly attributed to that page (not its child views', not descendant sub-pages')\n- [ ] Hovering a page's child view (when expanded) shows only that view's own navigation routes\n- [ ] Hovering a view node shows only navigation routes directly attributed to that view\n- [ ] Visibility logic reuses existing structural traversal helpers (`structuralDescendants`, `forest.childrenOf`) rather than introducing new ones\n- [ ] Code is reviewed and approved
